* **No version or hash check on runtime reload** – if the model file changes while workers are alive, they will keep the old model; you need a **reload‑on‑change** mechanism or a rolling restart.

        model = self._load_model()
        # batch inference could be added here
        with torch.no_grad():
            tensor = torch.tensor([self._encode(domain)], dtype=torch.long)

| 90‑93   | Marks alerts as `correlated = True` but **keeps them in memory** (no deletion).                                                              | 🟨       | Memory usage grows linearly with total processed alerts (even correlated ones).                                          | After marking as correlated, optionally **remove** them from the list (or move to a compacted “archived” store).             |
| 95      | Returns `None` when no incident is generated.                                                                                                | ✅       | Fine.                                                                                                                    |                                                                                                                              |
**Memory‑leak risk:** Over long runs, `active_alerts` will hold **all alerts** for the duration of `time_window_sec` (default 300 s). If the cleanup missed some entries due to a bug, memory would grow without bound. The current cleanup runs every minute and is O(N). For a high‑throughput SOC (hundreds of thousands of events per minute) this becomes a problem.
**Recommended changes**
* Move correlation state to an external **Redis Sorted Set** (`ZADD` with timestamp) – O(log N) inserts/expire.  
* Use Redis `EXPIRE` to auto‑evict entries after `time_window_sec`.  
* Keep the current in‑memory version only for unit tests.
